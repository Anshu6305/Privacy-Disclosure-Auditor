**Cross-Source Privacy Disclosure Consistency Auditor for Android Applications**
B.Tech major project, KIIT · six-member team · Phase 1–4 submission
Audit date: 15 November 2026 · Repository commit at audit time: `421f782` (branch `master`)

This document records what was cleaned, what was verified, where the
implementation agrees and disagrees with the approved Phase 1–3 documents, and
what remains incomplete. It is written to be checked, not to persuade. Every
figure in it was produced by a command run against this repository on the date
above, except where the text says otherwise and names the source.

## 5. Phase 1–4 consistency findings

The approved Phase 1 feasibility report, Phase 2 SRS and Phase 3 design document
were read directly for this audit (`Report_Phase-01/02/03.docx`). They are the
academic baseline and were **not** edited to match the implementation.

### Phase 1 — Feasibility

| Phase 1 statement | Implementation | Finding |
|---|---|---|
| Stack entirely open-source and familiar | React/Vite, FastAPI, PostgreSQL, SQLAlchemy, scikit-learn, PyTorch, Transformers, spaCy | **Consistent** |
| Cash expenditure ≈ ₹8,000–₹10,000 for the project | No paid service was introduced. Training ran on free-tier Colab T4 | **Consistent** |
| Development on 8 GB RAM, ~50 GB disk; GPU T4-class, intermittent | Encoder-scale models only; one model set resident at a time (DD-2); the two fine-tunes ran on a Colab T4 | **Consistent** |
| Verdict: FEASIBLE WITH CONDITIONS | The conditions that bit were corpus collection and span-extraction accuracy, both of which Phase 1 named as the least certain | **Consistent, and Phase 1's risk ranking proved correct** |

### Phase 2 — SRS

27 functional and 19 non-functional requirements, and the seven implementation
goals GI-01 to GI-07, are all present in the approved SRS and all are traced in
§6 below.

The approved exclusions hold. The system does **not** claim, anywhere in code,
API response or interface:

* legal or regulatory compliance verification — every report carries the scope
  sentence "It does not observe what the application actually does at runtime,
  and it is not a legal compliance finding";
* Android binary or runtime-traffic analysis — nothing in the codebase reads an
  APK or network capture;
* iOS support — no App Store code path exists;
* multilingual analysis — assumption A-01 restricts policies to English, and
  the pinned spaCy model is `en_core_web_sm`;
* user accounts or authentication — there is no user table and no auth code,
  which also satisfies NFR-13 by construction.

| Phase 3 design | Implementation | Finding |
|---|---|---|

| Data dictionary §10.2, ER diagram, DFD 0/1/2, class, sequence, activity, component, deployment, use-case, PERT | All present in the Phase 3 document and the diagram set (15 distinct diagrams) | **Consistent** |

**The two corpus deviations are the central honest finding of this submission.**
They are not implementation defects: the pipeline is generic and processes any
application whose two sources are supplied (§6, FR-01 to FR-26, and
`tests/unit/test_multi_application.py`). What is missing is collected data and
human annotation, both of which are collection and labelling effort rather than
code. Their consequence is that FR-27 cannot be satisfied and that no
system-level accuracy figure is defensible.

### Phase 4 — Implementation, verified against the repository

The ten statements the task asked to be treated carefully were each checked:

1. **One real application.** `data/corpus/apps/` holds exactly one record,
   `com.spotify.music`, `validation_status: manually_collected`, 19 Data Safety
   entries, both provenances `retrieval_mode: manual_import`, policy hash
   verified. **Confirmed.**
2. **Audit 13: 14 verdicts, 6 Consistent, 8 Undetermined, 18 evidence records.**
   Team-reported from `privacy_auditor_pilot`; **not independently verified in
   this audit**, because that database is not reachable from the agent session.
   Its internal consistency was checked and holds: 6 + 8 = 14; F-23 gives a
   Consistent verdict no evidence record, so all 18 must come from the 8
   Undetermined verdicts; F-22's recorder stores 1 to 3 records per Undetermined
   verdict, permitting 8 to 24; 18 is in range. The confirming SQL is in
   `docs/PHASE4_CLOSEOUT.md` §5.
3. **Three verdict types are fixture-only on real data.** Contradictory,
   In-policy-not-declared and Declared-not-in-policy have never appeared in a
   real-app audit. 81 verdict-engine tests exercise all five. **Confirmed and
   disclosed.**
4. **Multi-application capability is unit-tested, not demonstrated at scale.**
   6 tests; one application collected. **Confirmed.**
5. **OPP-115 is training data, not the cross-source gold set.** It labels
   privacy-policy segments with practice categories; the gold set FR-27 needs
   would label (application, category) pairs with cross-source verdicts.
   Different unit, different task. **Confirmed; the two are not conflated
   anywhere in the documentation.**
6. **The improved classifier is not uniformly better.** Macro-F1 0.6304 against
   the baseline's 0.7489; micro-F1, precision, Hamming loss and subset accuracy
   improve. **Confirmed; see §8.**
7. **Span extraction has limited exact-match performance.** Exact-match F1
   0.1072, overlap F1 0.5658. Described as a working prototype. **Confirmed.**
8. **Alignment and taxonomy mapping described as implemented.** F-18 is
   zero-shot NLI under approved decision D-01 Option A, not fine-tuned; F-15 is
   a rule table of 30 seeded entries with partial-mapping flags.
   **Confirmed.**
9. **F-34 sequential model loading remains incomplete.** The pipeline holds all
   three models for the duration of a run. **Still the case**, recorded in the
   consistency log at C-88 and unchanged since.
10. **Test figures.** Re-run today: 818 passed, 78 skipped, 0 failed; frontend
    33 passed. **Confirmed.**

## 8. Remaining gaps and limitations

**Model performance, as measured.** Same frozen policy-grouped split, seed
20261105, 541 held-out test segments:

| Metric | M5 baseline | F-11 improved |
|---|---:|---:|
| Macro-F1 | **0.7489** | 0.6304 |
| Micro-F1 | 0.7690 | **0.7775** |
| Precision | 0.7462 | **0.8231** |
| Recall | **0.7932** | 0.7367 |
| Hamming loss | 0.0545 | **0.0482** |
| Subset accuracy | 0.5896 | **0.6765** |

The improved classifier wins five of six aggregate measures and six of the ten
categories, and loses macro-F1 by 0.119 because it never predicts Data
Retention (7 positive test examples) or Do Not Track (4) at the 0.5 threshold.
Neither category has enough test examples to be a reliable measurement in
either model. User Access, Edit and Deletion also regresses, F1 0.538 against
0.774. Thresholds are provisional and were not tuned on test data. F-12 span
extraction: exact-match F1 0.1072, overlap F1 0.5658.

**No system-level accuracy claim is defensible.** There is no gold set, so the
end-to-end verdict accuracy of the auditor has never been measured. The figures
above are component metrics for the classifier and the span extractor, on
OPP-115, which is training data for practice classification and not a
cross-source evaluation set.

**Remaining limitations, in order of how much they constrain a claim:**

1. **No gold set, so FR-27 is not implemented and no end-to-end accuracy exists.** Phase 5.
2. **One application collected**, against a design expectation of 300–500. The capability is generic and unit-tested; the corpus is not.
3. **Three of five verdicts have never occurred on real data** — Contradictory, In-policy-not-declared, Declared-not-in-policy. All five are exercised by 81 controlled tests.
4. **Audit 13 is team-reported, not independently verified in this audit.** Its counts are internally consistent with F-22 and F-23.
5. **78 PostgreSQL integration tests skip** in any environment without `TEST_DATABASE_URL`; the team's separate run is the record.
6. **NFR-01, NFR-02, NFR-04 and NFR-19 were never measured.** Implemented, untimed.
7. **F-34 sequential model loading is not implemented**; all three models stay resident.
8. **The Docker worker image deliberately excludes the ML dependency set**, so it can claim an audit but not complete one. The verified run path is the local virtual environment.
9. **Span extraction is weak at exact match** and the aligner is zero-shot, not fine-tuned; F-18 fine-tuning needs 300–500 labelled pairs that do not exist.
10. Out of approved scope and never claimed: APK or runtime analysis, iOS, non-English policies, authentication, legal or compliance conclusions.
